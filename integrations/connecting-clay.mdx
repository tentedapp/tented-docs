Tented connects to [Clay](https://clay.com) so each prospect gets a personalized landing page built from an approved template. One HTTP API column starts generation; three delayed HTTP API columns check for the published page automatically. A final **Tented Result** column provides the fields for your campaign.

You can copy a setup prompt from Tented into Clay's Sculptor assistant, or configure the columns manually with the steps below.

## How it works

Clay tables can't be read or updated from outside on most plans, so Tented never calls Clay. Instead Clay calls Tented:

1. **Tented Start** sends the prospect's fields in a `POST`. Tented reserves a URL and returns HTTP `200` with `status: generating`, a `job_id`, and a `status_url`, while generation continues in the background.
2. **Tented Check 2m** waits 120 seconds, then makes a `GET` request to that status URL.
3. If the page is still generating, **Tented Check 5m** waits another 180 seconds and checks again. **Tented Check 8m** does the same if needed.
4. **Tented Result** selects the latest response for the current start. Campaign actions run only when it says `ready` and contains a URL.

Clay's [Delay Runs](https://www.clay.com/changelog/delay) support delays up to 10 minutes. The [delay starts after run conditions are met](https://university.clay.com/docs/enrichments), so use **120 + 180 + 180 seconds** for approximately 2, 5, and 8 minutes elapsed. Request and queue time may make checks later. Each check depends on the preceding column and skips once generation has stopped.

<Warning>
A URL with `status: generating` is a reserved address, not a live page. Delays automate checking; they do not guarantee publication. Rows still generating after the last check stay out of campaigns until a later check returns `ready` with a nonempty URL.
</Warning>

## Prerequisites

Before you begin, make sure you have:

- **Admin access** to your Tented workspace. Connecting, changing settings, and disconnecting are admin-only.
- **An approved tent template** in Tented. Pages are generated from a template's approved version. See [Templates](/working-with-tents/tent-templates) if you don't have one yet.
- **A Clay plan with access to the HTTP API enrichment and Delay Runs.** Check that both are available in your workspace before connecting.
- **AI credits**. Each generated page uses half a credit.

No Clay API key is needed.

## Step 1: Connect Clay in Tented

1. In Tented, open **Settings → Integrations**.
2. On the **Clay** tile, select **Connect**.

![The Integrations page with the Clay tile and its Connect button.](../images/clay-integrations-page.png)

3. In **Pages**, pick the approved **Tented template** each page starts from. For custom page instructions, expand **Advanced: generation prompt**. The `{{clay.rowData}}` token is replaced with the fields your Clay column sends.

![The Pages tab during setup, with a template selected and advanced instructions collapsed.](../images/clay-connect-pages.png)

4. Optionally open **Messages** to customize the **Link sentence** and **Follow-up sentence**. Leave either blank to omit it. Supported placeholders appear below the fields; `{{summary}}` becomes available in the automatic result checks after publication.

![The Messages tab groups both outreach sentences.](../images/clay-settings-messages.png)

5. Select **Connect & get settings**. The **Clay connection** tab opens. Expand **Connection details** for the endpoint and authentication header, with the secret masked by default. Three more expandable sections cover the start column, automatic checks, and campaign result.

![The Clay connection tab groups setup into expandable sections with a copyable assistant prompt.](../images/clay-settings-connection.png)

Use the endpoint and secret from your own workspace. Tented generates the secret; no Clay API key is needed.

For guided setup, select **Copy** beside **Set up with Clay's assistant**, paste the prompt into Sculptor, and select your saved HTTP API Headers account when asked. The prompt contains the endpoint, column names, delays, and formulas, but no secret. Review the generated configuration against this guide before running it. It asks Sculptor to leave table Auto-run paused and existing campaign actions unchanged.

Sculptor may create suggestions in **Sandbox Mode**. Accept each upstream suggestion with **Add column** before asking it to build the next dependent column. Use **Review changes** to inspect and apply the finished configuration. Avoid **Add and run 10 rows** during setup. Existing text-column names and test-row values may need to be entered manually.

Open each suggested HTTP column's **Configure** tab before saving. Verify the selected account, request fields, response-field list, delay, and run condition in the editor; Sculptor's summary can differ from the saved configuration. Remove any generated placeholder `Authorization` header: Tented uses `x-tented-webhook-secret` through your saved account.

<Note>
Each page uses half an AI credit. If your workspace runs out of credits, the integration pauses and resumes on its own once credits are available again.
</Note>

## Step 2: Add the start column in Clay

In the Clay table you want to enrich, select **Add column → Add enrichment**, search for **HTTP API**, and pick the **HTTP API** enrichment by Clay.

![Clay's enrichment search showing the HTTP API enrichment.](../images/clay-http-api-search.png)

For manual setup, switch to the **Configure** tab and name the column **Tented Start**. Fill in the inputs with the values Tented shows:

| Setting | Value |
|---|---|
| Method | `POST` |
| Endpoint | The per-workspace URL from the Tented dialog |
| Body | The JSON below, with each value pointed at a column |
| Headers | A saved HTTP API Headers account containing `x-tented-webhook-secret` and the secret from Tented |
| Response values to return | The ten fields listed below |
| Run settings | Run immediately; save without running while setting up |

```json
{
  "email": "",
  "first_name": "",
  "last_name": "",
  "company_name": "",
  "job_title": "",
  "website": ""
}
```

Paste the body, then put the cursor between each pair of quotes, type `/` and pick the column from the menu Clay opens (for example your Work Email column for `email`). Each pick becomes a column chip inside the quotes. A value that stays plain text is sent as text, so a pasted `"/Work Email"` would not work.

<Tip>
For a waterfall column such as Clay's **Work Email**, the menu first shows the column as a group with its providers inside. Open the group and pick the plain **Work Email** entry at the bottom of the list, not one of the providers.
</Tip>

![The configured body with a column chip in each value.](../images/clay-column-config-body.png)

`email` is required; it is how Tented recognizes a row it has already seen. Add any other columns the page should know about (industry, LinkedIn URL, notes) as extra keys: everything in the body is given to the page generator.

Select a saved [HTTP API Headers account](https://university.clay.com/docs/http-api-integration-overview) in the column's **Account** section for authentication. If that option is unavailable, add `x-tented-webhook-secret` directly under **Headers** as a key/value pair and keep it private. Reuse this authentication for all four HTTP columns.

To create the saved account, open **Clay Settings → Connections → Create → HTTP API (Headers)**. Give it a recognizable name such as **Tented page generation**, add `x-tented-webhook-secret` as the key and the secret from Tented as its value, then save. Select this account in each HTTP column; keep the secret out of Sculptor chat and formulas.

Under **Response values to return**, add each field below as a separate entry. Press **Enter** after each field name and verify that all ten entries appear before saving.

| Field | Contents |
|---|---|
| `job_id` | An opaque polling reference. A new POST returns a fresh reference, even for an existing page. |
| `status_url` | The complete URL for a GET check; use it unchanged and supply the same authentication header. |
| `should_poll` | `true` only while `status` is `generating`; use this boolean for conditional checks. |
| `poll_after_seconds` | Suggested delay: 120 after a generating POST, 180 after a generating GET, or 0 for a terminal result. |
| `checked_at` | The time of this response, in UTC. |
| `tented_url` | A reserved URL while generating; the current published URL when ready; empty when unavailable |
| `tented_page_offer` | The link sentence with the URL filled in |
| `tented_page_reference` | The follow-up sentence |
| `tented_page_summary` | A one-line description, returned by checks after publication when available |
| `status` | `generating`, `ready`, `failed`, or `unavailable`; see the readiness steps below |

Leave table Auto-run paused until the full workflow is configured. Column Auto-run alone does not poll a pending response; the delayed columns below provide those checks.

To finish, open the arrow next to **Save** and choose **Save and don't run**, so you can try one row before the whole table runs.

![The Save menu with Save and don't run.](../images/clay-save-menu.png)

## Step 3: Add automatic result checks

Add three more **HTTP API** columns with method **GET**, no body, the same saved header account, and the same ten response fields. Map each **Endpoint** to the preceding column's `status_url` using a Clay column chip. Do not paste the displayed chip notation as a literal URL.

Under **Run settings**, enable column **Auto-run**, choose **Run after delay**, and set these values:

| Column name | Endpoint from | Delay in seconds | Only run if |
|---|---|---|---|
| **Tented Check 2m** | Tented Start → status_url | `120` | Tented Start → should_poll is `true` |
| **Tented Check 5m** | Tented Check 2m → status_url | `180` | Tented Check 2m → should_poll is `true`, and its job_id matches Tented Start → job_id |
| **Tented Check 8m** | Tented Check 5m → status_url | `180` | Tented Check 5m → should_poll is `true`, and its job_id matches Tented Start → job_id |

For example, the **Tented Check 5m** condition is:

```javascript
{{Tented Check 2m}}?.should_poll === true &&
{{Tented Check 2m}}?.job_id === {{Tented Start}}?.job_id
```

The exact conditions for all three checks have copy buttons in **Edit settings → Clay connection → Automatic result checks**. Use Clay's formula editor to map the named references to your actual columns. Keep the endpoint reference required so a check cannot run without a URL.

Matching `job_id` prevents a saved response from an earlier start from being used by a new check chain. `ready`, `failed`, and `unavailable` all return `should_poll: false`, stopping later checks. GET checks never retry generation or use Tented AI credits; Clay may charge for HTTP actions according to your plan.

## Step 4: Collect one result for campaigns

Add a **Formula** column named **Tented Result**, returning an object:

```javascript
[
  {{Tented Check 8m}},
  {{Tented Check 5m}},
  {{Tented Check 2m}},
  {{Tented Start}}
].find(result => result?.job_id &&
  result.job_id === {{Tented Start}}?.job_id) || null
```

Allow missing or skipped check columns: disable required-data toggles for the three optional check references if Clay shows them. This lets an immediately ready start, or a ready first check, reach the result without waiting for checks that will never run. The formula selects the latest response for this start, keeping its status, URL, and message fields together. It also prevents an older `ready` response from overriding a later `failed` or `unavailable` response.

Extract `status`, `tented_url`, `tented_page_offer`, `tented_page_reference`, and `tented_page_summary` from **Tented Result** as needed. Map campaign values from this final result. On the downstream campaign sync or send action, set **Only run if** to:

```javascript
!!{{Tented Start}}?.job_id &&
{{Tented Result}}?.job_id === {{Tented Start}}?.job_id &&
{{Tented Result}}?.status === "ready" &&
!!{{Tented Result}}?.tented_url
```

Keep campaign actions disabled while configuring and testing. An empty fallback in a message controls formatting; it does not establish readiness, because a generating result already contains a reserved URL.

## Step 5: Test and enable the workflow

1. Use one safe test row with downstream campaign actions disabled. Enable both [table and column Auto-run](https://university.clay.com/docs/table-management-settings) for the workflow, with no other rows scheduled to run.
2. Run **Tented Start** for that row. HTTP `200` confirms acceptance; open the response to see `job_id`, `status_url`, and `status: generating` (or `ready` if this prospect already has a published page).
3. Watch **View activity** in Tented. Clay's first check runs after about two minutes; subsequent checks run only if needed. Generation time varies with workload, credits, and publication limits.
4. Verify that **Tented Result** becomes `ready` with the current URL and message fields even when later checks are skipped. Open the URL and preview your campaign mappings before enabling the campaign action.
5. Run **Tented Start** on the intended remaining rows. With Auto-run enabled, new rows follow the same automatic check chain.

If a row remains `generating` after the last check, inspect Tented activity. Once the underlying issue is resolved, run its latest GET cell again or add a deliberate later delayed check and include it first in **Tented Result**. A failed job requires an explicit POST retry. The workflow does not poll indefinitely or automatically spend credits retrying failures.

<Tip>
The column recipe and header secret remain available at **Edit settings → Clay connection**, including after your first row succeeds. Use the same instructions when adding another Clay table.
</Tip>

## Existing tables and later campaign batches

If you already use a single Tented HTTP column, keep its POST body and authentication, rename it **Tented Start**, and add the five metadata response fields: `job_id`, `status_url`, `should_poll`, `poll_after_seconds`, and `checked_at`. Add the checks and final result described above, then update your campaign mappings and condition. Existing saved responses do not gain metadata automatically: run the start column for the intended rows with downstream actions disabled to initialize the new workflow.

Recheck before a later campaign batch, even if a saved result says `ready`. Running **Tented Start** again returns a fresh reference and the current publication state; an existing completed page is reused without generating or charging for another page. Failed rows may retry generation, so inspect the scope of a bulk POST run. A GET against an existing `status_url` only reads the result. If rechecking a GET cell, use the latest check represented in **Tented Result**, so an older saved check cannot override it.

Keep pages published while their campaigns are running. A saved Clay result is a snapshot: unpublishing a page later does not update existing table cells or remove leads already synced to a campaign.

## What happens after connecting

The Clay tile shows the template, the last sync, and a **View activity** link.

![The Clay tile after connecting, showing the template and last sync.](../images/clay-card-connected.png)

**Page URLs are readable.** Each page publishes at a path built from the row's name and company, for example `https://your-domain/for-bryan-from-acme-co`. When a row has no company, the path uses the first and last name; without a first name, a short random path is used instead.

**Activity** lists each run with the pages published, rows skipped, and credits used.

![The Clay activity dialog listing recent syncs.](../images/clay-activity.png)

**Generated tents** appear in your Tents list with "Clay Integration" as the creator. Use **Filter → Hide integration-created** to keep them out of the way while you work on other tents.

![The Tents list with Clay Integration as the creator.](../images/clay-tents-list.png)

Each page is built from your template and the row's fields, so the prospect sees their own name and company:

![A published page personalized for a Clay row.](../images/clay-published-page.png)

**GET checks never start or retry generation.** Changing row data does not rebuild an existing page. Retry a failed attempt explicitly by running **Tented Start** again: Tented resumes an existing draft when possible; if a new page must be generated, that generation uses credits.

**Email identifies the prospect across your workspace.** Calls for the same normalized email, including from different Clay tables, reuse the same page. Use a different email only for a different prospect, not as a way to refresh a page.

**Readiness reflects publication when the cell runs.** If you change a published page's alias, the next run returns its current URL. If you unpublish or delete a completed page, the next run returns `unavailable` with empty URL, sentence, and summary fields. Tented does not automatically create a replacement for an intentionally removed page. Republishing the same page restores `ready` on the next check.

## Changing settings

Select **Edit settings** on the Clay tile. The modal has three tabs:

| Tab | What you can do |
|---|---|
| **Pages** | Choose a template and expand the advanced generation prompt. These changes apply to new pages. |
| **Messages** | Edit the link and follow-up sentences returned on future Clay requests. |
| **Clay connection** | Copy the setup prompt, endpoint, and header secret, or expand the start, check, and campaign instructions. |

![The Edit settings Pages tab keeps advanced instructions collapsed and the modal focused.](../images/clay-settings-pages.png)

Edits stay with you when switching tabs. Select **Save changes** in the footer to apply them. Saving settings does not regenerate existing pages or update previously saved Clay responses; fetch a fresh result to see updated sentences.

## Disconnecting

Select **Disable** on the Clay tile. New requests to the old connection fail. Tented keeps published pages and releases unused reserved paths. A draft that has already claimed its path is retained so a new connection can finish publishing it; it is not reported as ready until publication is confirmed.

When reconnecting, replace the POST endpoint and shared authentication in Clay with those from the new connection, then run **Tented Start** to get new polling references. Old status URLs cannot be reused. Tented remembers completed pages and reuses them. Rows whose unused reservations were released can receive a new URL, so check readiness again before sending.

## Troubleshooting

| What you see | What it means | What to do |
|---|---|---|
| Cell error **The row needs an email address** | The body has no `email` key, the mapped column is empty for that row, or the value is plain text instead of a column reference. | In the column's body, put the cursor inside the quotes after `"email":`, type `/` and pick the email column. |
| Cell error **Body must be a JSON object** | The body is not a JSON object (for example a bare string or a list). | Paste the JSON body from the Tented dialog again. |
| Cell error **401** | The header secret is missing or wrong. | Open **Edit settings → Clay connection** in Tented and paste the header name and secret again. |
| GET error **400 / INVALID_JOB** | The polling reference is missing, malformed, or belongs to a different connection. | Map the complete `status_url` from the preceding response without editing it. |
| GET error **404 / JOB_NOT_FOUND** | This attempt was replaced or removed. | Run **Tented Start** to get a current reference. |
| Cell error **410** | The integration was disconnected in Tented. | Connect again and update the column with the new URL and secret. Rows that already have a page keep their URL. |
| **Paused: out of AI credits** | The workspace has no credits left for new pages. | Add credits. The integration resumes on its own. |
| **Paused: published-tent limit reached** | Your plan's limit on published tents is reached. | Unpublish tents or upgrade your plan. |
| Checks never start | Auto-run is off, or a condition or endpoint reference is misconfigured. | Check both table and column Auto-run, the preceding response's `should_poll`, and the mapped `status_url`. Delay begins only after conditions are met. |
| Final result is empty after an early `ready` | A skipped later check is incorrectly required. | Make the check references optional in the final formula and confirm its column mappings. |
| `status` stays `generating` after eight minutes | The page is still building, paused, or the response is stale. | Check **Activity**. Fetch a later GET result after resolving the issue; keep the row out of campaigns until `ready`. Adding credits resumes Tented's worker, but does not restart a finished Clay check chain. |
| `status` is `failed` | Tented retired this attempt. GET does not retry it. | Check **Activity**, fix the cause, then run **Tented Start** to retry. |
| `status` is `unavailable` and the URL is empty | A previously completed page is unpublished or deleted. | Republish the existing page if appropriate, then fetch a fresh result. A deleted page is not automatically replaced. Remove or pause any campaign lead that still holds its old URL. |
